1. What are the steps of the write protococ/operation in GFS?
   * **My response:** The write in GFS have the data and the control flows separated. Firstly, the client contacts the master and asks for the chunk server which is responsible for that chunk. If no server is responsible for that chunk, the master chooses a primary chunk server and provides a lease for that chunk. The lease is automatically renewed if the chunk is still actively written. Then the data flows from the client to one of the chunk servers. Then the chunk server transmit the data to the nearest chunk server and so on until all the chunk servers have all the data. When all the data is set inside the cache memory of all the chunk server, the client sends a write message to the primary, and after that all the chunk servers write data onto their disks. If all the writes are succesfull, the primary inform the client that the write is succesfull.
   * **AI response:** In GFS, the write operation separates the control flow from the data flow to maximize network throughput. The process follows these steps:
     * Querying the Master: The client asks the Master which chunkserver holds the current lease for the chunk (the primary) and the locations of the secondary replicas. If no primary exists, the Master assigns a lease to one of the replicas.
     * Caching the Data (Data Flow): The client pushes the data directly to all replicas. To optimize bandwidth, the data is pushed linearly along a chain of chunkservers (pipelining) based on network proximity. The chunkservers store this data in an internal LRU buffer cache, not yet writing it to disk.
     * Initiating the Write (Control Flow): Once all replicas acknowledge receipt of the data, the client sends a formal write request to the primary chunkserver.
     * Serialization and Execution: The primary assigns consecutive serial numbers to all mutations happening on the chunk to ensure order. It applies the mutations locally and forwards the write command (with the serial numbers) to all secondary replicas, which apply them to their disks in the exact same order.
     * Acknowledgment: The secondaries reply to the primary indicating success. Finally, the primary replies to the client, confirming the write is complete.

2. What is the chunk size in GFS and what are the benefits of using that chunk size?
   * **My response:** In GFS the chunk size is of 64MB. This chunk size is great for storing large files, while minimazing the number of metadata needed to store in order to correcty address them.
   * **AI response:** In GFS, the standard chunk size is 64 MB, which is significantly larger than typical file system block sizes. This deliberate design choice provides three major benefits:
     * Reduces Master Interactions: Because chunks are large, a client can perform many reads or writes on the same chunk without needing to contact the Master again to ask for location metadata. This severely reduces network overhead and prevents the Master from becoming a bottleneck.
     * Minimizes Metadata Size: It allows the Master to keep all file metadata comfortably in its main memory (RAM). This enables ultra-fast metadata lookups and management.
     * Reduces Network Overhead: By working with larger chunks, clients can maintain a single persistent TCP connection to a chunkserver for longer periods, reducing the overhead involved in constantly setting up and tearing down connections.

3. How does a client write to HDFS? (Explain the write operations and pipelining)
   * **My response:** The client asks the NameNode for the DataNodes responsible for that file. The NameNode responds with a list of IP addresses. The client then connects to the nearest DataNode and starts to send data in chunks of 64KB. Then a chain of connections is created in order to transport this data to all the DataNodes. For each received and succesfully written packet, an ack is sent back up, following the chain connection. When all the acks goes back to the original DataNode (all ndoes gave their ack), the client is informed that the write was succesfull
   * **AI response:** The HDFS write operation relies on a master/slave architecture and a pipelined data transfer mechanism. The process works as follows:
     * Requesting a Block: The client contacts the NameNode to create a new file. The NameNode checks permissions and, if approved, returns a list of DataNodes that will host the replicas for the first block of the file.
     * Setting up the Pipeline: Instead of the client sending data to all DataNodes simultaneously, it forms a pipeline. The client connects to the first DataNode, the first connects to the second, and the second connects to the third.
     * Streaming Data in Packets: The client buffers the data and splits the block into smaller 64 KB packets. It pumps these packets into an internal data queue. The first DataNode receives a packet, buffers it to its local memory, and immediately forwards it to the second DataNode in the pipeline, and so on.
     * Packet Acknowledgment (ACK): As each DataNode finishes writing a packet to its local storage, it sends an ACK back up the pipeline in reverse order. The client maintains an ack queue to track verified packets.
     * Closing the File: Once all packets for the block are successfully written and acknowledged, the client closes the pipeline. If the file requires more blocks, it requests a new set of DataNodes from the NameNode and repeats the process. Finally, it tells the NameNode the write is complete.

The data does not pass from the NameNode, the data transmission is directly between the DataNode and the client.    * **AI response:** HDFS is heavily inspired by GFS and implements a Master/Slave architecture built on top of the TCP/IP layer, specifically utilizing RPC (Remote Procedure Call) for control commands and a specialized TCP-based streaming protocol for data transfer. The architecture consists of two main components:
     * The NameNode (Master): It manages the file system namespace, directory tree, and file-to-block mappings. It maintains all of this metadata in its main memory (RAM) for rapid access.
     * The DataNodes (Slaves): They store and retrieve the actual blocks of data as directed by the NameNode and handle the read/write requests directly from clients. Crucially, application data never flows through the NameNode; clients talk directly to DataNodes for data transfer to prevent bottlenecks.
     Communication and Reliability Mechanisms:
     * Heartbeats: DataNodes send periodic 'Heartbeats' to the NameNode to signal that they are alive. These heartbeats piggyback essential status information, such as available storage capacity.
     * Block Reports: Periodically, DataNodes send a 'Block Report' to the NameNode. This is a list of all local blocks stored on that node, allowing the NameNode to maintain an accurate map of where every block replica resides in the cluster.
     * Replication: For fault tolerance, HDFS automatically replicates data blocks across multiple DataNodes (typically using a default replication factor of 3, guided by a rack-awareness policy).

6. Describe Dynamo’s partitioning algorithm.
   * **My response:** Dynamo partitions data using consistent hashing of the key. Once we have the hash of the key, we use that do identify the node in the ring responsible for that hash. The responsible node is the first node met clockwise. The node than saves the key toghether with the data and it's then propagated to N successive servers for data replication
   * **AI response:** Dynamo uses an advanced variant of Consistent Hashing to partition data across a distributed token ring. The Hash Ring: The output range of a hash function (like MD5 or SHA-1) is treated as a fixed circular ring. Both the data keys and the cluster nodes are hashed to determine their positions on this ring. The Clockwise Assignment: To find which node is responsible for a key, the system hashes the key and walks clockwise along the ring until it encounters the first node. This node is designated as the coordinator for that key. The Innovation: Virtual Nodes (Vnodes): Instead of mapping a physical machine to a single point on the ring, Dynamo maps each physical machine to multiple virtual nodes (vnodes) spread across the ring. This solves two problems: Load Balancing: It ensures a highly uniform distribution of data across the cluster. Heterogeneity: A highly powerful server can be assigned more vnodes, while a weaker server can be assigned fewer. Replication Mechanism: For fault tolerance, the coordinator node doesn't just store the key locally; it replicates the data by forwarding it to the $N-1$ successive distinct physical nodes clockwise down the ring (known as the preference list).

8. What properties does Dynamo guarantee?
   * **My response:** Dynamo guarantees high availability at the cost of consisteny. Dynamo uses "eventual consistency", meaning that eventually, all nodes will agree on a value.
   * **AI response:** The core design philosophy of Amazon's Dynamo is to maximize availability and predictability at scale. It offers the following distinct properties and guarantees:
     * High Availability with an 'Always-Writable' Policy: Dynamo guarantees that the system will almost never reject a write operation. To achieve this, it relaxes traditional ACID properties in favor of BASE (Basically Available, Soft State, Eventual Consistency). If a network partition occurs, writes are accepted on whatever nodes are reachable.
     * Eventual Consistency with Tunable Quorums: While data is eventually consistent across all replicas, the system guarantees that consistency can be tuned using the formula $R + W > N$. If an application requires stronger consistency, it can trade off some latency or availability by increasing the read ($R$) or write ($W$) quorum sizes.
     * Strict Latency SLAs (99.9th Percentile): Unlike systems that optimize for average or median response times, Dynamo guarantees performance metrics at the 99.9th percentile. This means 999 out of 1000 requests are guaranteed to execute within tight, single-digit millisecond boundaries, preventing high-tail latency amplification.
     * Client-Managed Conflict Resolution: Dynamo guarantees that any data conflicts arising from simultaneous writes during a partition are preserved using Vector Clocks. Rather than dropping data, it guarantees that all conflicting versions (siblings) are returned to the client application during a subsequent read, allowing the client to resolve the discrepancy.

11. What is the difference between Orchestration and Choreografy
    * **My response:** Orchestration and Choreografy are two approaches to SOA architectures. Orchestration is an approach that uses a central node called orchestrator that manages the interaction with all the services. The services do not know each other and the orchestrator manages comunication and interaction between them.     * **AI response:** Orchestration and Choreography are two distinct design patterns used to coordinate workflows and communications across services in distributed systems, SOA, and microservices:
      * Orchestration (The Conductor Metaphor): In Orchestration, a centralized controller—the Orchestrator—acts as a 'conductor.' How it works: The orchestrator explicitly directs the flow of the entire business process. It sends a request to Service A, waits for the response, and then decides to call Service B or handle an error. Key Characteristics: Centralized: The orchestrator owns the state and logic of the workflow. Decoupled Services: The individual services are 'dumb' regarding the overall business process; they only know how to execute their specific task when told. Pros/Cons: It provides great visibility over the workflow state, but the orchestrator itself can become a bottleneck and a single point of failure.
      * Choreography (The Dancers Metaphor): In Choreography, there is no central controller. Instead, the services act like a troupe of 'dancers' who follow a shared music cue. How it works: It is typically implemented using an Event-Driven Architecture. When Service A finishes its task, it publishes an event (e.g., 'OrderCreated') to a message broker. Service B and Service C listen for that event and independently react to it. Key Characteristics: Decentralized: Each service is autonomous and manages its own role in the workflow. Event-Driven: Communication is asynchronous, minimizing temporal coupling. Pros/Cons: It is highly scalable, flexible, and has no single point of failure. However, tracking the overall state of a complex, multi-step business process can be much harder to monitor and debug.

12. What are the three ways of scaling in microservices?
    * **My response:** We can scale microservices by using the scale cube. The scale cube defines scaling in this three dimentions:
      * The horizontal one, by adding more machines that works toghether with the others to run the microservices in parallel.
      * The functional scomposition one, by splitting the microservices code in even smaller parts that can be scaled singularly
      * The data partitioning (or sharding) one, by using a known identifier to split data between microservices (like using an ID for informations related to a single tenant)
    * **AI response:** We can scale microservices across three distinct dimensions using the Scale Cube model. This model defines scaling along the X, Y, and Z axes:
      * 1. The X-Axis: Horizontal Duplication (Cloning). How it works: This is the most common form of scaling. It involves running multiple identical instances of a microservice behind a load balancer. The load balancer distributes incoming requests evenly among the instances. Key Aspect: It is highly effective for increasing overall throughput, but every instance still runs the entire codebase of that service and has access to all the data.
      * 2. The Y-Axis: Functional Decomposition (Splitting by Verb/Noun). How it works: Instead of cloning a massive monolithic service, we split the application's monolithic codebase into smaller, independent microservices based on functional responsibilities (e.g., separating an e-commerce app into an Order Service, a Product Service, and a Billing Service). Key Aspect: This allows us to scale only the specific services under heavy load. For example, if product browsing is highly active but orders are low, we can scale up the Product Service without wasting resources on the Billing Service.
      * 3. The Z-Axis: Data Partitioning (Sharding by Customer/Attribute). How it works: Similar to X-axis scaling, we run multiple identical instances of a service, but each instance is responsible for only a specific subset of the data. Key Aspect: A router at the entry point uses an attribute of the request (like a User ID or Tenant ID) to direct the request to the correct instance. For example, Instance 1 handles premium enterprise customers, while Instance 2 handles free-tier users. This is incredibly useful for scaling databases and geographically distributing services.

    * **AI response:** In Kubernetes, self-healing is the platform's ability to automatically detect and recover from application or infrastructure failures without human intervention. This is a practical implementation of an autonomous control loop (similar to a MAPE-K loop), where Kubernetes constantly drives the cluster's actual state to match the declared desired state. Specifically, Kubernetes implements self-healing through three main mechanisms:
      * Container & Pod Healing (via Probes): The Kubelet continuously monitors container health using Liveness Probes. If a container crashes, becomes unresponsive, or fails this probe, the Kubelet automatically restarts it based on the Pod's restartPolicy.
      * Application Scaling & Replacement (via Controllers): High-level controllers like ReplicaSets or Deployments constantly monitor the number of running Pods. If a worker node fails, taking several Pods down with it, the controller detects that the actual Pod count is lower than the desired count. It automatically schedules replacement Pods onto healthy nodes.
      * Node Health Monitoring (Node Controller): The control plane monitors node heartbeats. If a node goes offline or becomes unhealthy (marked as NotReady), the Node Controller waits for a grace period and then evicts the Pods from that node, allowing the scheduler to recreate them on healthy nodes.
