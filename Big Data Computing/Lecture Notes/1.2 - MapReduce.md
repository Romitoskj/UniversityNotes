## 2. The MapReduce Abstraction (§1)

### 2.1 Functional Roots

MapReduce borrows two core operations from functional programming:

1. **`map(f, list)`:** Applies function \(f\) independently to every element of a list, producing a new list. Because each element is processed independently, `map` calls have no state dependencies and can be executed in parallel.
2. **`reduce(g, list)`:** Combines elements of a list pairwise using function \(g\), producing an aggregated result.

### 2.2 User-Defined Functions (UDF Signature)

From the programmer's perspective, a MapReduce job requires implementing only two functions:

\[\text{map}(k_1, v_1) \longrightarrow \text{list}(k_2, v_2)\] \[\text{reduce}(k_2, \text{list}(v_2)) \longrightarrow \text{list}(v_3)\]

- **Map Function:** Takes a single input \((k_1, v_1)\) pair from HDFS/GFS, processes it independently, and emits zero, one, or many intermediate \((k_2, v_2)\) pairs. Map functions are **stateless** and have no visibility into other input records.
- **Reduce Function:** Takes an intermediate key \(k_2\) along with the **complete list of all intermediate values** emitted for that key across all Map tasks, and emits final output values. Different keys are processed independently in parallel.

### 2.3 Canonical Examples

#### Example 1: Word Count

- **Goal:** Count occurrences of every distinct word across a petabyte-scale corpus of documents.

```
# Map Phase: Emits (word, 1) for every word observed
def map(document_id, document_text):
    for word in document_text.split():
        emit(word, 1)

# Reduce Phase: Sums all 1s received for a given word
def reduce(word, list_of_counts):
    total = sum(list_of_counts)
    emit(word, total)
```

_Notice that the Map phase only observes and emits pairs; no aggregation occurs until the Reduce phase receives all 1s grouped by word._

#### Example 2: Inverted Index Construction

- **Goal:** Map each word to a sorted list of unique document IDs containing it.

```
def map(document_id, document_text):
    for word in document_text.split():
        emit(word, document_id)

def reduce(word, list_of_document_ids):
    emit(word, unique_sorted(list_of_document_ids))
```

_The underlying framework code remains identical; only the emitted values and aggregation logic change._

### 2.4 The Determinism Requirement

For MapReduce's fault tolerance to hold, Map and Reduce functions **must be pure and deterministic**. Given the same input, they must always produce identical outputs and produce no side effects (such as mutating external databases or relying on global state). Determinism ensures that re-executing a failed task on a different machine produces identical results.

## 3. Execution Architecture & Data Flow (§2)

### 3.1 Job Coordination & Task Allocation

Execution is coordinated by a central master node (**Master / JobTracker**):

1. The Master splits the input dataset into independent blocks.
2. **Map Task Creation:** By default, the framework instantiates **one Map task per input storage block** (e.g., 64 MB or 128 MB blocks from HDFS/GFS).
3. **Data Locality Scheduling:** Following the principle _"move computation to data"_, the Master schedules Map tasks on the physical machine holding the requested block. If the local machine is busy, it falls back to a node on the same rack, and lastly to an off-rack node.

```
Data Locality Hierarchy:
  [Local Node Disk] ──(Best: 0 network cost)──► Map Task
  [Same Rack Node]  ──(Fallback: intra-rack switch)──► Map Task
  [Off-Rack Node]   ──(Last resort: cross-rack switch)──► Map Task
```

4. **Over-Decomposition:** The number of Map tasks is significantly larger than the number of worker nodes, allowing workers to execute waves of tasks for finer-grained load balancing and straggler mitigation.

### 3.2 Intermediate Output & Local Disk Writes

Unlike final output, **intermediate Map output is written to the local disk** of the worker machine executing the Map task (not to HDFS/GFS). Because intermediate data is temporary and consumed solely by the subsequent Reduce phase, avoiding DFS replication saves substantial network and storage overhead.

### 3.3 Partitioning Intermediate Keys

To ensure all values for a key arrive at the same Reduce task, a **partitioning function** maps intermediate keys to one of \(R\) designated Reduce tasks:

\[\text{partition}(\text{key}) = \text{hash}(\text{key}) \pmod R\]

- **Hash Partitioning:** Distributes keys uniformly across Reduce tasks.
- **Reducer Count (\(R\)):** \(R\) is a user-configurable parameter. Setting \(R\) too low causes "hot" overloaded reducers, while setting \(R\) too high increases shuffle coordination overhead and creates small output files. A common guideline is setting \(R\) to a small multiple of available worker nodes.

### 3.4 Local Pre-Aggregation: Combiner Functions

A **Combiner** is an optional mini-reduce step executed locally on the Map worker's local disk output prior to sending data across the network. When the Reduce function is associative and commutative (e.g., addition in Word Count), running the Reducer function as a Combiner sums counts locally (e.g., turning thousands of `(word, 1)` pairs into a single `(word, 500)` pair), significantly slashing network transfer volume during shuffle.

```
Without Combiner: Map Output ──► [network] ──► (word, 1), (word, 1), (word, 1)... (10,000 times)
With Combiner:    Map Output ──► [Local Pre-sum] ──► [network] ──► (word, 10000)
```

### 3.5 Sharded Final Output

Each Reduce task writes its final results directly back to the distributed file system (HDFS/GFS) as a distinct output shard (e.g., `part-r-00000`, `part-r-00001`).

## 4. The Shuffle & Sort Phase (§3)

### 4.1 What Is the Shuffle?

The **Shuffle** phase is the all-to-all communication step that routes intermediate output from \(M\) Map tasks across the network to \(R\) Reduce tasks. Every Reducer must pull its corresponding partition region from every Map worker's local disk.

```
  Map Task 1 (Local Disk) ──┬──────────────┬──────────────┐
                            │              │              │
  Map Task 2 (Local Disk) ──┼──────────────┼──────────────┤
                            │              │              │
  Map Task 3 (Local Disk) ──┴──────────────┴──────────────┘
                            ▼              ▼              ▼
                        Reduce 1       Reduce 2       Reduce 3
```

### 4.2 Why Shuffle Is the Primary Cost Center

The shuffle phase is frequently the primary performance bottleneck of a MapReduce job due to compounding overheads:

1. **Network Overhead:** Involving \(M \times R\) potential transfers, total network traffic is proportional to the total intermediate data volume \(D\) across the cluster.
2. **Disk I/O Overhead:** Data is written to local disk by Mappers, read back during HTTP transfers, and written/sorted on the Reducer side.

### 4.3 Grouping via Intermediate Sorting

Before running user-defined `reduce` calls, each Reduce task merges and **sorts its received data by intermediate key**.

Sorting guarantees that all values for a key are contiguous in memory/disk. This abstracts away key-grouping logic from the programmer, allowing `reduce()` to simply iterate over grouped keys sequentially.

## 5. Fault Tolerance & Stragglers (§4)

### 5.1 Worker Failure & Task Re-Execution

Workers maintain periodic **heartbeat pinging** with the Master.

- **Map Task Recovery:** If a Map worker fails or times out, all Map tasks assigned to it (even completed ones) must be re-executed on another worker, because their intermediate outputs stored on local disk are now unreachable.
- **Reduce Task Recovery:** If a Reduce worker fails, only in-progress or failed Reduce tasks are re-executed. Completed Reduce task outputs do not need re-computation because they are already safely replicated in HDFS/GFS.
- **Idempotency & Atomic Commits:** When tasks are re-executed, atomic file rename operations coordinated by the Master ensure that only one completed attempt's output is written to the final namespace.

### 5.2 Master Failure

If the Master process crashes, the standard recovery policy is to **abort and restart the job**. Because a Master process only lives for the duration of a single job (unlike a long-lived NameNode), restarting the job is an acceptable simplicity trade-off.

### 5.3 The Straggler Problem & Speculative Execution

A **straggler** is a task that runs exceptionally slowly without outright crashing (e.g., due to degraded disk performance, bad CPU cores, network contention, or data skew). Because a job's completion time is bottlenecked by its slowest task, stragglers can degrade total runtime significantly.

```
Without Speculation: Task 1..999 [10s] ────────────────────────► Straggler Task 1000 [200s] ──► Job Finish (200s)
With Speculation:    Task 1..999 [10s] ──► Backup Task 1000 [10s] ──► Job Finish (~20s)
```

- **Mechanism:** Near the end of a job stage, the Master identifies tasks running significantly slower than average and launches **backup (speculative) task copies** on idle workers.
- **Resolution:** Whichever attempt finishes first (original or backup) is accepted as final, and the losing attempt is terminated.
- **Trade-Off:** Speculative execution trades spare cluster compute resources for lower tail-latency.

## 6. Synthesis: Strengths & Limitations (§5)

### 6.1 System Comparison: Storage vs. Compute

```
Aspect                  Storage Layer (Lec 1.1 - GFS/HDFS)     Compute Layer (Lec 1.2 - MapReduce)
--------------------------------------------------------------------------------------------------
Coordinator             Master / NameNode                      Master / JobTracker
Worker Unit             Chunkserver / DataNode                 Map Task / Reduce Task
Failure Detection       Heartbeats                             Heartbeats
Recovery Strategy       Block Re-replication                   Task Re-execution
Primary Cost Center     Disk Space & Network Writes            Shuffle (Network All-to-All & Local Disk I/O)
Unique Feature          Rack-Aware Placement                   Speculative Execution
```

### 6.2 Major Strengths

- **High Abstraction:** Programmers write sequential logic; the framework manages distributed execution.
- **Built-in Fault Tolerance:** Deterministic tasks combined with re-execution handle crashes transparently.
- **Data Locality:** Seamless integration with HDFS/GFS block locations minimizes cluster network loading.

### 6.3 Core Limitations & Transition to Spark (Lecture 1.3)

1. **Disk-Heavy Pipeline:** Intermediate data must be written to disk between stages. Iterative algorithms (e.g., Machine Learning gradient descent or PageRank) pay heavy disk and shuffle costs repeatedly across steps.
2. **Rigid Two-Stage Model:** Multi-stage queries require chaining independent MapReduce jobs, forcing data back through HDFS/GFS at every job boundary.
3. **High Latency:** Optimised for high-throughput batch processing rather than interactive or streaming queries.

_These limitations directly motivate **Apache Spark** (Lecture 1.3), which introduces in-memory Resilient Distributed Datasets (RDDs) and Directed Acyclic Graph (DAG) execution plans._
