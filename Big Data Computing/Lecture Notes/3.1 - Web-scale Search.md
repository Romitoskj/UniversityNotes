1. System Scale and The Web-Scale Retrieval Problem

1.1 Formalizing the Retrieval Task

Web-scale information retrieval is framed as a mapping from a user's natural language query to an ordered, ranked subset of relevant text documents selected from a massive collection.

- **Corpus (**$D$**):** A collection of $N$ documents, where $N \approx 10^{10}$ (tens of billions of indexed web pages).
- **Query (**$q$**):** An ordered sequence of search terms $q = (t_1, t_2, \dots, t_{|q|})$ drawn from a global vocabulary $V$.
- **Candidate Pool (**$C_q$**):** A subset of documents containing one or more query terms, where $|C_q| \approx 10^4 - 10^6$ pages ($C_q \ll N$).
- **Result Set (**$R_k$**):** The top-$k$ most relevant documents ($k \approx 10$), ranked in strictly descending order of relevance score.

```
+-------------------------------------------------------+
|                 Full Corpus (D)                       |
|               N ≈ 10^10 documents                     |
+-------------------------------------------------------+
                           |
                           |  Phase 1: Candidate Selection
                           v  (Inverted Index Lookup & Merge)
+-------------------------------------------------------+
|               Candidate Pool (C_q)                    |
|             10^4 to 10^6 documents                    |
+-------------------------------------------------------+
                           |
                           |  Phase 2: Relevance Scoring
                           v  (TF-IDF / Cosine + Min-Heap)
+-------------------------------------------------------+
|                 Top-k Results (R_k)                   |
|                   k ≈ 10 documents                    |
+-------------------------------------------------------+
```

1.2 Systems Scale and Latency Constraints

Search engines operate under strict Service Level Objectives (SLOs):

- **Document Scale:** $N \approx 10^{10}$ documents.
- **Throughput Demand:** $10^4$ queries per second (tens of thousands of concurrent requests).
- **Latency Budget:** 99th percentile (P99) response time $\le 200\text{ ms}$.

Infeasibility of Naive Linear Scanning

Assuming an average document length $L \approx 10^3$ tokens, checking whether query terms exist across an unindexed corpus requires scanning: $$\text{Work} = O(N \cdot L) \approx 10^{10} \times 10^3 = 10^{13}\text{ tokens per query}$$

To satisfy a 200 ms latency window via a linear scan, a system would need to process hundreds of terabytes per second of memory bandwidth per query. Consequently, web search engines must achieve **sub-linear retrieval time** ($o(N)$) by precomputing an inverted search index.

1.3 The Two Sub-Problems of Web Retrieval

Web-scale retrieval decouples search execution into two sequential stages:

1. **Candidate Selection (Boolean / Filtering Phase):** Rapidly reduces the corpus from $N$ to $C_q$ by selecting documents that contain the query terms. This step prioritizes high recall and relies on inverted index traversals.
2. **Relevance Scoring (Ranking Phase):** Evaluates candidate documents $d \in C_q$ using mathematical relevance models (e.g., TF-IDF, vector space cosine similarity) combined with query-independent web graph signals (e.g., PageRank). This step prioritizes high precision for the top-$k$ positions.

2. Fundamental Data Structure: The Inverted Index

2.1 Forward Index vs. Inverted Index

- **Forward Index (**$\text{Document} \to \text{Terms}$**):** Stores the sequence of words contained within each document ID. Answering "Which documents contain term $t$?" requires scanning every document entry ($O(N \cdot L)$).
- **Inverted Index (**$\text{Term} \to \text{Documents}$**):** Maps each distinct term directly to an ordered list of document IDs in which it appears. Answering the same query requires a single dictionary lookup followed by reading the specific term's list ($O(|C_q|)$).

```
FORWARD INDEX (Doc -> Terms)              INVERTED INDEX (Term -> Docs)

Doc 1: [big, data, spark]                 big     -> (Doc 1, Doc 2)
Doc 2: [big, data, hadoop]    INVERT      data    -> (Doc 1, Doc 2, Doc 3)
Doc 3: [data, science]       ========>    hadoop  -> (Doc 2)
                                          science -> (Doc 3)
                                          spark   -> (Doc 1)
```

2.2 Anatomy of an Inverted Index

An inverted index comprises two main components:

1. **Dictionary (Vocabulary** $V$**):** An in-memory data structure (e.g., Trie, B-Tree, or Hash Table) containing all distinct normalized terms. For each term $t$, it stores:
    - The **Document Frequency (**$df_t$**)**: The total number of documents containing term $t$.
    - A **Posting Pointer**: The memory/disk address pointing to the start of term $t$'s posting list.
2. **Posting Lists:** Contiguous or linked blocks stored on disk or in cluster RAM. A posting list for term $t$ consists of individual **postings** strictly sorted by Document ID ($\text{docID}$): $$\text{Posting List}(t) = \langle (\text{docID}_1, tf_{t, d_1}), (\text{docID}_2, tf_{t, d_2}), \dots, (\text{docID}_{df_t}, tf_{t, d_{df_t}}) \rangle$$
    - $\text{docID}$: Unique numerical identifier assigned to a document.
    - $tf_{t,d}$: **Term Frequency**, representing the occurrences of term $t$ in document $d$. (Positional offsets inside the document may also be included to support phrase queries).

2.3 Sparse Matrix View and Compressed Sparse Row (CSR)

The collection can be conceptualized as a term-document incidence matrix $M$ of size $|V| \times N$, where $M_{i,j} = 1$ if term $i$ occurs in document $j$, and $0$ otherwise.

- **Matrix Dimensions:** $|V| \approx 10^7$ distinct terms, $N \approx 10^{10}$ documents $\implies 10^{17}$ cells.
- **Sparsity:** With average document length $\bar{L} \approx 10^3$, the number of non-zero entries is $\bar{L} \cdot N \approx 10^{13}$.
- **Density:** $\frac{10^{13}}{10^{17}} = 10^{-4} = 0.01\%$ (over $99.99\%$ sparse).

Storing $M$ as a dense array would require petabytes of zero-value storage. An inverted index is equivalent to applying **Compressed Sparse Row (CSR)** format to the term-document incidence matrix by storing only non-zero entries (the $1\text{s}$) grouped by row.

2.4 Sub-Linear Vocabulary Growth: Heaps' Law

**Heaps' Law** models the empirical growth of vocabulary size $|V|$ relative to the total number of processed text tokens $T$: $$|V| = K_{\text{Heaps}} \cdot T^\beta$$ where $K_{\text{Heaps}} \in [10, 100]$ and $\beta \in [0.4, 0.6]$.

Because $\beta < 1$, doubling the corpus size does not double the vocabulary. Even across billions of documents ($T \approx 10^{13}$), the total vocabulary size $|V|$ remains in the range of tens of millions of terms. Consequently, the dictionary easily fits into server RAM (tens to hundreds of megabytes), whereas posting lists grow linearly with $T$ and dominate total index storage.

3. Inverted Index Construction & MapReduce

3.1 The Linguistic Preprocessing Pipeline

Raw HTML pages gathered by crawlers pass through a multi-stage text processing pipeline before index insertion:

1. **Raw Crawl Parsing:** Strips HTML/JS markup and extracts raw text buffers.
2. **Tokenization:** Emits a stream of raw tokens delimited by whitespace and punctuation. Edge cases include hyphenated terms (_state-of-the-art_), email addresses, and URLs.
3. **Linguistic Normalization:**
    - **Case Folding:** Converts characters to lowercase (_Big_ $\to$ _big_).
    - **Accent Stripping:** Removes diacritics (_résumé_ $\to$ _resume_).
    - **Stemming (e.g., Porter Stemmer):** Removes morphological suffixes to reduce words to their common root (_computing_, _computed_ $\to$ _comput_).
    - **Stopword Handling:** Highly frequent terms (_the_, _is_, _at_) may be filtered or stored in compressed auxiliary structures.

3.2 Sort-Based Construction Bottleneck

Transforming normalized text into an index requires creating $(\text{term}, \text{docID})$ tuples and re-ordering them:

$$\langle \text{docID: } 1, \text{ terms: [big, data]} \rangle \implies (\text{big}, 1), (\text{data}, 1)$$

Index construction is fundamentally a **sorting problem**. To form posting lists, all identical terms across the corpus must be grouped contiguously and sorted by $\text{docID}$.

For $K \approx 10^{12}$ total postings, the sorting phase has a time complexity of $O(K \log K)$. Because $K$ far exceeds the main memory (RAM) capacity of any single machine, sorting must be performed using external-memory algorithms (such as Blocked Sort-Based Indexing, BSBI) or distributed framework infrastructure.

3.3 MapReduce Indexing Architecture

Index construction fits natively onto the **MapReduce** framework:

- **Map Phase:** Mappers ingest document chunks from distributed storage (HDFS/GFS). For each document $d$, the mapper tokenizes/normalizes the text and emits key-value pairs: $$\text{Key: } \text{term } t, \quad \text{Value: } (\text{docID } d, tf_{t,d})$$
- **Shuffle & Sort Phase:** The MapReduce framework automatically partitions pairs by term key $t$, routes all values for term $t$ to a single reducer node, and sorts the values primary by term and secondary by $\text{docID}$.
- **Reduce Phase:** Each reducer receives a term $t$ and a stream of sorted tuples $\langle (d_1, tf_1), (d_2, tf_2), \dots \rangle$. The reducer computes $df_t$, compresses the posting list, and writes out the final inverted index partition.

```
MAP PHASE                  SHUFFLE & SORT                 REDUCE PHASE
(Parse Docs)               (Route & Sort by docID)        (Write Postings)

Mapper 1 (Doc 1-3)
 -> (big, 1), (data, 1)    =================>  Reducer 1 (Term: "big")
                                                -> Postings: (1,1), (2,1), (5,1)
Mapper 2 (Doc 4-6)         =================>  Reducer 2 (Term: "data")
 -> (big, 2), (big, 5)                          -> Postings: (1,1), (4,1), (9,1)
```

4. Posting List Compression

4.1 Storage Imperative

Uncompressed 64-bit integers for $10^{12}$ postings require 8 TB of raw memory just for document IDs (excluding $tf$ and positions). Because NVMe SSDs ($\approx 50\ \mu\text{s}$) and mechanical disks ($\approx 10\text{ ms}$) introduce severe latency penalties relative to RAM access ($\approx 100\text{ ns}$), active posting lists must reside in cluster RAM to satisfy the sub-200 ms query budget. Compression enables fitting terabytes of posting data into available RAM.

4.2 Gap (Delta) Encoding

Because posting lists are sorted by $\text{docID}$ ($\text{docID}_1 < \text{docID}_2 < \dots < \text{docID}_k$), storing raw IDs wastes space on large leading bits. **Gap encoding** stores the relative difference ($\Delta$) between consecutive IDs instead:

$$\Delta_1 = \text{docID}_1, \quad \Delta_i = \text{docID}_i - \text{docID}_{i-1} \quad \text{for } i > 1$$

Expected Gap Size Analysis

Assuming terms are distributed uniformly across $N$ documents, the expected gap size for term $t$ is: $$E[\Delta] = \frac{N}{df_t}$$

- **Frequent Terms (**$df_t \approx 10^8, N = 10^{10}$**):** $E[\Delta] = \frac{10^{10}}{10^8} = 100$. Representing an integer of magnitude 100 requires only $\lceil \log_2(100) \rceil = 7\text{ bits}$ (compared to 64 bits for raw $\text{docID}$s).
- **Rare Terms (**$df_t \approx 10^2$**):** $E[\Delta] = 10^8$, requiring $\approx 27\text{ bits}$. However, because their posting lists contain only 100 elements, their total footprint is small.

Gap encoding naturally allocates fewer bits to frequent terms, which make up the vast majority of index size.

4.3 Variable-Byte (VB) Encoding

Variable-Byte (VB) encoding compresses integers into byte-aligned sequences. Each byte uses **7 bits for payload** and **1 bit (the 8th, most significant bit) as a continuation flag**:

- Continuation Bit = `1`: More bytes follow for this integer.
- Continuation Bit = `0`: Final byte of the current integer.

```
Byte Structure: [ C | P6 | P5 | P4 | P3 | P2 | P1 | P0 ]
                 ^   └───────────────────────────────┘
                 │                 Payload (7 bits)
                 └ Continuation Bit (1 = more bytes follow, 0 = last byte)
```

VB Worked Encodings

- **Example 1: Gap = 5**
    - Binary: `101` (3 bits $\le 7$ bits).
    - Fits in 1 byte. Continuation bit = `0`.
    - Byte: `[00000101]` $\implies$ `0x05`.
- **Example 2: Gap = 130**
    - Binary: `10000010` (8 bits $\implies$ requires 2 bytes).
    - Least Significant 7 bits: `0000010`. Continuation bit = `0` $\to$ `[00000010]` (`0x02`).
    - Remaining upper bits: `1` padded to 7 bits $\to$ `0000001`. Continuation bit = `1` $\to$ `[10000001]` (`0x81`).
    - Encoded Byte Stream: `10000001 00000010` $\implies$ `0x81 0x02`.

4.4 Bit-Level Compression: Golomb-Rice Encodings

For ultra-dense posting lists ($E[\Delta] < 8$), byte alignment limits maximum compression to 8 bits per posting. Bit-aligned schemes like **Golomb-Rice coding** split a gap $\Delta$ into a quotient $q = \lfloor \frac{\Delta - 1}{m} \rfloor$ and a remainder $r = (\Delta - 1) \bmod m$:

- The quotient $q$ is encoded in unary ($q$ ones followed by a `0`).
- The remainder $r$ is encoded in binary using $\log_2(m)$ bits.
- When parameter $m$ is chosen as a power of 2 ($m = 2^k$, Rice coding), division and modulo reduce to bitwise shifts and masks, compressing frequent-term postings down to 4–8 bits per item.

4.5 Compression Schemes Summary

|Encoding Scheme|Bits / Posting|Compression Ratio|CPU Decoding Cost|Primary Use Case|
|---|---|---|---|---|
|**Raw 64-bit docID**|64 bits|$1\times$ (baseline)|None|In-memory uncompressed arrays|
|**Variable-Byte (VB)**|8–16 bits|$4\times - 8\times$|Very Low (byte-aligned)|Industrial standard web search|
|**Golomb-Rice**|4–8 bits|$8\times - 16\times$|Moderate (bit-shift bound)|Ultra-dense posting list storage|

5. Query Processing: Merges, Acceleration, and Scoring

5.1 Boolean Merges

Boolean queries are evaluated as set operations over posting lists:

- $\text{Query } (t_1 \text{ AND } t_2)$: Set intersection of $\text{PostingList}(t_1) \cap \text{PostingList}(t_2)$.
- $\text{Query } (t_1 \text{ OR } t_2)$: Set union of $\text{PostingList}(t_1) \cup \text{PostingList}(t_2)$.

Because posting lists are strictly sorted by $\text{docID}$, intersection executes via a two-pointer linear merge algorithm in $O(n_1 + n_2)$ time, where $n_1, n_2$ are the lengths of the lists.

```
def intersect(list1, list2):
    answer = []
    p1, p2 = 0, 0
    while p1 < len(list1) and p2 < len(list2):
        if list1[p1] == list2[p2]:
            answer.append(list1[p1])
            p1 += 1
            p2 += 1
        elif list1[p1] < list2[p2]:
            p1 += 1
        else:
            p2 += 1
    return answer
```

For multi-term AND queries ($t_1 \text{ AND } t_2 \text{ AND } \dots \text{ AND } t_m$), terms are processed in order of **increasing document frequency (**$df_t$**)**. Intersecting the smallest list first constrains the candidate set early, minimizing subsequent processing time.

5.2 Merge Acceleration: Skip Pointers

When intersecting a short list (length $L_{\text{short}}$) with a long list (length $L_{\text{long}}$), scanning every element of the long list is inefficient. **Skip pointers** add forward links across the posting list to bypass irrelevant document spans.

```
Long List:  [1] -> 3 -> 5 -> [8] -> 12 -> 15 -> [20] -> 24 -> 30 -> [45] -> 60
             │                ▲                  ▲                   ▲
             └─ skip to 8 ────┴── skip to 20 ────┴─── skip to 45 ────┘

Short List: [24]
Execution: Sitting at 1, target is 24.
           - Skip to 8  (8 <= 24)  -> Jump!
           - Skip to 20 (20 <= 24) -> Jump!
           - Skip to 45 (45 > 24)  -> Do not skip! Scan linearly: 24 (Match!).
```

Skip Evaluation Strategy

At position $p_1$ with a skip pointer target $S(p_1)$ and a target document ID $d_{\text{target}}$ from the short list:

- If $S(p_1) \le d_{\text{target}}$, advance pointer $p_1$ directly to $S(p_1)$ (skipping intermediate elements).
- If $S(p_1) > d_{\text{target}}$, fall back to standard linear scanning step-by-step.

Optimal Skip Interval

Placing skip pointers every $\sqrt{L}$ elements balances jump distance and evaluation overhead, reducing intersection complexity from $O(L)$ to $O(\sqrt{L})$.

5.3 Vector Space Model and Relevance Scoring

Unranked Boolean retrieval returns unranked sets that can contain millions of documents. Search engines rank candidates using statistical relevance weights based on the **Vector Space Model**.

TF-IDF Weighting Scheme

- **Term Frequency (**$tf_{t,d}$**):** Measures local term frequency within document $d$.
- **Inverse Document Frequency (**$idf_t$**):** Measures the global rarity of term $t$ across corpus $D$: $$idf_t = \log \left( \frac{N}{df_t} \right)$$
- **Compound Weight:** $w_{t,d} = tf_{t,d} \times idf_t$.

Cosine Similarity Score

The relevance score of document $d$ relative to query $q$ is defined as the cosine of the angle between their vector space representations:

$$\text{Score}(q, d) = \cos(\theta) = \frac{\vec{q} \cdot \vec{d}}{\|\vec{q}\| \|\vec{d}\|} = \frac{\sum_{t \in q \cap d} w_{t,q} \cdot w_{t,d}}{\|\vec{q}\| \|\vec{d}\|}$$

For a given query $q$, $\|\vec{q}\|$ is constant across all candidate documents and can be omitted during ranking. The document norm $\|\vec{d}\| = \sqrt{\sum_{t \in d} w_{t,d}^2}$ is precomputed offline. Scoring simplifies to calculating the dot product over non-zero terms present in both $q$ and $d$:

$$\text{Score}(q, d) \propto \frac{1}{\|\vec{d}\|} \sum_{t \in q \cap d} w_{t,q} \cdot w_{t,d}$$

5.4 Query Evaluation Paradigms: TAAT vs. DAAT

Accumulating term score contributions across candidate documents follows one of two primary loop paradigms:

```
TERM-AT-A-TIME (TAAT)                     DOCUMENT-AT-A-TIME (DAAT)

Outer Loop: Query Terms                   Outer Loop: Document IDs (Lockstep)
Inner Loop: Posting Lists                 Inner Loop: Query Term Pointers

  Term 1 (big)                              Doc 1: [Term 1, Term 2] -> Score & Heap
   ├─ Doc 1 -> Accumulator A[1]              Doc 2: [Term 1, Term 2] -> Score & Heap
   └─ Doc 2 -> Accumulator A[2]              Doc 3: [Term 2]         -> Score & Heap
  Term 2 (data)
   ├─ Doc 1 -> Accumulator A[1]
   ├─ Doc 2 -> Accumulator A[2]
   └─ Doc 3 -> Accumulator A[3]
```

Term-At-A-Time (TAAT)

- **Execution Flow:** The outer loop iterates over query terms $t \in q$. For a given term, the algorithm processes its entire posting list sequentially, updating an in-memory accumulator table $A[d]$ for every candidate document $d$.
- **Pros:** Accesses posting lists in purely sequential reads, optimizing hardware cache usage.
- **Cons:** Requires maintaining accumulators for _every_ document that contains at least one query term. Memory usage can explode for common terms ($O(|C_q|)$).

Document-At-A-Time (DAAT)

- **Execution Flow:** The outer loop iterates through document IDs in numeric order. Posting list pointers for all query terms advance in lockstep. For each candidate document $d$, the algorithm computes its total score at once and passes it to a bounded **min-heap of size** $k$.
- **Min-Heap Maintenance:** The min-heap stores the current top-$k$ highest-scoring documents. The root of the heap holds the lowest score in the top-$k$ set ($\text{score}_{\min}$). For a candidate document $d_{new}$:
    - If $\text{Score}(q, d_{new}) \le \text{score}_{\min}$, discard $d_{new}$.
    - If $\text{Score}(q, d_{new}) > \text{score}_{\min}$, remove the root and insert $d_{new}$, rebalancing the heap in $O(\log k)$ time.
- **Pros:** Bounded memory footprint ($O(|q| + k)$). Because document scores are finalized immediately, DAAT supports early termination algorithms (such as WAND or MaxScore) that skip low-scoring documents without fully evaluating them.
- **Cons:** Requires simultaneous, concurrent reads across multiple posting lists.

Comparative Summary: TAAT vs. DAAT

|Dimension|Term-At-A-Time (TAAT)|Document-At-A-Time (DAAT)|
|---|---|---|
|**Loop Hierarchy**|Outer: Query terms; Inner: Posting elements|Outer: Document IDs; Inner: Query pointers|
|**Memory Footprint**|Unbounded ($O(|C_q|
|**Read Pattern**|Sequential scan per posting list|Synchronized lockstep traversal across lists|
|**Score Finalization**|Only after all posting lists are read|Finalized immediately per document|
|**Early Termination**|Difficult|Highly effective (WAND / MaxScore)|
|**Industry Usage**|Specialized batch systems|Standard in commercial search engines|

6. Distributed Partitioning Architectures

Because a global web index spans multi-terabyte posting data and serves thousands of queries per second, the index must be sharded across a cluster of $K$ physical machines.

```
DOCUMENT PARTITIONING (Column Cuts)          TERM PARTITIONING (Row Cuts)

       Docs 1-N/2      Docs N/2-N                   All Docs (1-N)
     +------------+  +------------+             +--------------------+
T1   |  Shard 1   |  |  Shard 2   |        T1-3 |      Shard 1       |
T2   | (Full Vocab|  | (Full Vocab|             +--------------------+
T3   |  Local Docs|  |  Local Docs|        T4-6 |      Shard 2       |
     +------------+  +------------+             +--------------------+
```

6.1 Document Partitioning (Horizontal Sharding)

- **Architecture:** The corpus $D$ is split into $K$ disjoint subsets ($D_1, D_2, \dots, D_K$). Each shard node maintains a self-contained local inverted index spanning its assigned document subset across the full vocabulary $V$.

```
Query q
   │
   ├─► Broadcast to Shard 1 ──► Local DAAT ──► Top-k List 1 ┐
   ├─► Broadcast to Shard 2 ──► Local DAAT ──► Top-k List 2 ┼─► Result Aggregator ──► Global Top-k
   └─► Broadcast to Shard K ──► Local DAAT ──► Top-k List K │  (Priority Merge)
```

Query Flow

1. A **Query Router** receives request $q$ and broadcasts it to **all** $K$ **shards**.
2. Each shard executes local query processing (DAAT) over its index partition and returns its local top-$k$ results $\langle (\text{docID}, \text{score}) \rangle$ to a central **Result Aggregator**.
3. The Result Aggregator merges $K \times k$ candidate tuples using a priority queue (min-heap) to compute the global top-$k$ set.

Strengths

- **Zero Inter-Node Communication During Scoring:** Shards evaluate candidate relevance scores independently without exchanging posting data.
- **Trivial Scale-Out:** Adding new documents simply requires deploying additional shards without modifying existing index partitions.
- **Fault Isolation:** If a single shard fails, the system loses access to only a fraction ($1/K$) of the corpus.

Weaknesses & The Straggler Problem

Because the global top-$k$ results could reside on any node, every query must fan out to all $K$ shards. The overall query latency is bounded by the slowest responding node:

$$\text{Latency}_{\text{query}} = \max_{i \in \{1, \dots, K\}} (\text{Latency}_{\text{Shard}_i})$$

If individual nodes have an independent probability $p = 0.01$ (1%) of suffering a latency spike, the probability $P_{\text{delayed}}$ that a query is delayed by at least one straggler node grows exponentially with shard count $K$:

$$P_{\text{delayed}} = 1 - (1 - p)^K$$

- For $K = 69$ shards: $P_{\text{delayed}} = 1 - (0.99)^{69} \approx 50\%$.
- For $K = 100$ shards: $P_{\text{delayed}} = 1 - (0.99)^{100} \approx 63.4\%$.

Over 63% of incoming user requests would hit tail latency spikes without mitigations like hedged requests or aggressive replication.

6.2 Term Partitioning (Vertical Sharding)

- **Architecture:** The global vocabulary $V$ is partitioned into $K$ disjoint term subsets ($V_1, V_2, \dots, V_K$). Each node holds the complete posting lists across all $N$ corpus documents for its subset of terms.
- **Query Flow:** A query router analyzes terms in query $q$ and sends request tasks only to the specific nodes holding those terms.

Weaknesses & Network Bottlenecks

1. **Network Bandwidth Saturation:** Evaluating multi-term queries ($t_1 \text{ AND } t_2$) requires transmitting full posting lists over the datacenter network to a single node for intersection. For common terms with millions of postings, transmitting tens of megabytes per query over network switches consumes bandwidth and violates the 200 ms latency budget.
2. **Severe Load Imbalance (Zipfian Skew):** Term frequencies follow a power-law distribution (Zipf's Law). Nodes holding high-frequency terms (_web_, _news_) become severe CPU and memory bottlenecks, while nodes holding rare terms remain largely idle.

6.3 Partitioning Paradigms Comparison

|Feature / Metric|Document Partitioning|Term Partitioning|
|---|---|---|
|**Partition Key**|Document ID Range / Hash|Term String Range / Hash|
|**Query Routing**|Broadcast to **all** $K$ shards|Selective fan-out to $|
|**Inter-Node Traffic**|Small top-$k$ tuples ($K \times k$)|Full posting lists (tens of MBs)|
|**Load Balancing**|Uniform (documents hashed evenly)|Highly skewed (Zipfian term distribution)|
|**Straggler Impact**|High (bounded by slowest shard)|Low (only contacts query-term nodes)|
|**Production Usage**|**Dominant standard in search engines**|Specialized batch/niche systems|

7.1 Multi-Tier Caching

1. **Tier 1 — Query Result Cache:** An LRU cache located at the front-end string router that maps normalized query strings directly to fully pre-rendered top-$k$ HTML snippet responses. Because query popularity follows a power-law distribution, caching handles 30% to 50% of total search traffic with sub-5 ms latency.
2. **Tier 2 — Posting List Cache:** Caches decompressed posting lists for common terms in node RAM, avoiding repetitive variable-byte decoding steps during candidate scoring.

7.2 Replication: Throughput and Availability

Each document shard is copied across $R$ physical servers (typically $R = 3$ across distinct server racks).

- **Throughput Scaling:** Aggregate query capacity scales linearly with replica factor $R$.
- **High Availability & Fault Tolerance:** If a shard replica crashes or stalls, the query router dynamically fails over to an operational replica, insulating user latency from node failures.

7.3 Blended Ranking: Integrating Offline Authority Signals

Textual similarity alone ($S_{\text{text}}(q,d)$) cannot distinguish high-quality authoritative web pages from low-quality or spam pages that match query terms. Modern search engines blend online textual scores with offline structural graph priors:

- **Online Query-Dependent Signal (**$S_{\text{text}}(q,d)$**):** Computes vector space cosine similarity over inverted index postings during query execution.
- **Offline Query-Independent Signal (**$P(d)$**):** Computes structural authority metrics (such as PageRank) over the web hyperlink graph offline.
- **Blended Score Function:** $$\text{Score}_{\text{final}}(q, d) = \alpha \cdot S_{\text{text}}(q, d) + (1 - \alpha) \cdot P(d)$$ where $\alpha \in [0, 1]$ balances term relevance matching against global authority.

Quiz Answer Key

Answer 1

Web-scale retrieval maps a corpus $D$ ($N \approx 10^{10}$ docs) and a query $q$ to a ranked top-$k$ set $R_k$ ($k \approx 10$). A naive scan costs $O(N \cdot L)$, requiring $10^{13}$ token comparisons per query; serving this within a 200 ms P99 latency budget at $10^4$ queries/sec would demand hundreds of TB/s of memory bandwidth, which is hardware-infeasible without precomputed inverted indices.

Answer 2

A forward index maps document IDs to contained terms, requiring $O(N \cdot L)$ scans to locate words. An inverted index maps terms to sorted posting lists of document IDs, enabling sub-linear $O(|C_q|)$ lookups. It is mathematically equivalent to Compressed Sparse Row (CSR) storage because it explicitly stores only the non-zero entries (the $1\text{s}$) of the highly sparse ($> 99.99\%$) term-document incidence matrix.

Answer 3

Heaps' Law states $|V| = K_{\text{Heaps}} \cdot T^\beta$ (where $\beta \in [0.4, 0.6]$ and $T$ is total token count). Because $\beta < 1$, vocabulary growth is sub-linear; as the corpus grows to billions of documents, the dictionary remains small enough to fit in server RAM (tens to hundreds of MBs), while posting lists grow linearly ($O(T)$) and dominate total storage footprint.

Answer 4

The pipeline consists of: (1) Raw Crawl Parsing to strip HTML/JS markup; (2) Tokenization to split text into distinct term streams on whitespace and punctuation; (3) Case Folding to convert text to lowercase; (4) Accent Stripping; (5) Stemming (e.g., Porter Stemmer) to chop suffixes to common morphological roots; and (6) Stopword Handling to filter or compress highly frequent words.

Answer 5

Creating posting lists requires collecting all identical terms across documents and re-ordering them strictly by term and $\text{docID}$, which requires sorting $K \approx 10^{12}$ tuples in $O(K \log K)$ time—a workload that exceeds single-machine memory. MapReduce solves this by using Mappers to extract tuples, Shuffle & Sort to route and sort key-value pairs by term and $\text{docID}$ across cluster nodes, and Reducers to write out compressed posting lists.

Answer 6

Gap encoding stores the relative differences ($\Delta_i = \text{docID}_i - \text{docID}_{i-1}$) between consecutive sorted posting entries rather than raw 64-bit IDs. For frequent terms with high document frequencies ($df_t$), the expected gap $E[\Delta] = N / df_t$ is small (e.g., 100), requiring only 7 bits to store, whereas rare terms produce large gaps but have very short posting lists overall.

Answer 7

Variable-Byte encoding uses 7 payload bits per byte and 1 continuation bit (bit 7, where `1` = more bytes follow, `0` = last byte). For $\Delta = 130$ (binary `10000010`): the lower 7 bits (`0000010`) are written to the terminal byte with continuation bit `0` (`0x02`), and the remaining upper bit (`1` $\to$ `0000001`) is written to the preceding byte with continuation bit `1` (`0x81`), yielding the 2-byte sequence `0x81 0x02`.

Answer 8

TAAT loops over query terms sequentially, updating accumulators for all candidate documents; DAAT advances pointers across query posting lists in lockstep by $\text{docID}$, finalizing scores immediately per document and maintaining a bounded min-heap of size $k$. DAAT is preferred in web search engines because its memory usage is bounded ($O(|q| + k)$) and it enables early termination optimization algorithms like WAND.

Answer 9

Document Partitioning shards the corpus horizontally (each node holds a full vocabulary index for $1/K$ of the docs), requiring query broadcasting but zero inter-node communication during scoring. Term Partitioning shards the vocabulary vertically (each node holds global postings for $1/K$ of the terms), avoiding broadcast but requiring massive network transfers of full posting lists during multi-term intersections and suffering severe Zipfian load imbalances.

Answer 10

Tail latency amplification occurs because document-partitioned queries fan out to all $K$ shards, making overall response time dependent on the slowest node ($\max_i T_i$). The probability of a query hitting a straggler delay is $P_{\text{delayed}} = 1 - (1 - p)^K$. For $K = 100$ and $p = 0.01$, $P_{\text{delayed}} = 1 - (0.99)^{100} = 1 - 0.366 = 0.634$ (63.4% of queries are delayed).

Comprehensive Glossary

- **Candidate Selection:** The initial phase of an information retrieval pipeline that uses boolean inverted index lookups to quickly filter a corpus of $N$ documents down to a candidate pool $C_q$ of potentially relevant pages.
- **Case Folding:** A linguistic normalization process that converts all text characters to lowercase to unify matching across term variants.
- **Compressed Sparse Row (CSR):** A matrix storage format that stores only non-zero values alongside row pointers and column indices. The inverted index is a domain-specific implementation of CSR applied to the term-document incidence matrix.
- **Document Frequency (**$df_t$**):** The total count of distinct documents in the collection that contain term $t$.
- **Document Partitioning:** A horizontal sharding architecture where a corpus is divided into $K$ disjoint document subsets. Each shard maintains a self-contained local inverted index spanning its document subset for the full vocabulary.
- **Document-At-A-Time (DAAT):** A query processing paradigm where the outer evaluation loop iterates across document IDs in numeric order, advancing query term posting pointers in lockstep to compute final document scores immediately.
- **Forward Index:** A data structure mapping document IDs to the sequence of terms contained within each document.
- **Gap (Delta) Encoding:** A compression technique that stores the numerical difference ($\Delta_i = \text{docID}_i - \text{docID}_{i-1}$) between consecutive sorted postings instead of full raw document IDs.
- **Golomb-Rice Coding:** A bit-level compression scheme optimal for geometrically distributed gaps that splits integers into a unary-encoded quotient and a bitwise binary-encoded remainder.
- **Heaps' Law:** An empirical formula ($|V| = K_{\text{Heaps}} \cdot T^\beta$) modeling sub-linear vocabulary growth relative to total corpus tokens $T$.
- **Inverse Document Frequency (**$idf_t$**):** A logarithmic metric ($\log(N / df_t)$) quantifying the global rarity of term $t$ across a document collection.
- **Inverted Index:** A core search engine data structure mapping each distinct term in a vocabulary to a sorted posting list of document IDs containing that term.
- **MapReduce:** A distributed programming paradigm (comprising Map, Shuffle & Sort, and Reduce phases) used to construct inverted indices at scale by parallelizing pair extraction and term sorting.
- **Posting:** An individual record within a posting list containing a document ID ($\text{docID}$) and optional metadata such as term frequency ($tf_{t,d}$) or position offsets.
- **Posting List:** A list of postings for a given term, strictly sorted by document ID.
- **Query Fan-Out:** The action of broadcasting a search query from a router to multiple shard nodes in a distributed index cluster.
- **Relevance Scoring:** The second phase of retrieval, which ranks candidate documents using mathematical models (such as vector space cosine similarity or TF-IDF) combined with authority scores.
- **Skip Pointers:** Additional forward pointers embedded within posting lists at fixed intervals (typically $\sqrt{L}$) to accelerate list intersection by bypassing non-matching document IDs.
- **Stemming:** A linguistic normalization process (e.g., Porter Stemmer) that chops word suffixes to reduce morphological variants to a shared root form.
- **Straggler Problem (Tail Latency Amplification):** Latency degradation in multi-node broadcast systems where total request latency is constrained by the slowest responding node.
- **Term Frequency (**$tf_{t,d}$**):** The number of times term $t$ occurs within document $d$.
- **Term Partitioning:** A vertical sharding architecture where the global vocabulary is split across $K$ nodes, with each node holding complete posting lists across all corpus documents for its subset of terms.
- **Term-At-A-Time (TAAT):** A query processing paradigm where the outer evaluation loop iterates through query terms sequentially, updating score accumulators in memory for all candidate documents.
- **Variable-Byte (VB) Encoding:** A byte-aligned integer compression format using 7 bits per byte for data payload and 1 bit as a continuation flag.
- **Vector Space Model:** An algebraic framework representing text documents and search queries as high-dimensional vectors of term weights to calculate relative cosine similarity scores.
- **Zipf's Law:** A power-law distribution observing that term frequencies in natural language text are inversely proportional to their frequency rank.
