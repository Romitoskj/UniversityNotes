## 1. Context & Motivation: Beyond the Two-Stage Model

- **Course:** Big Data Computing (M.Sc. Computer Science, Sapienza University of Rome).
- **Lecturer:** Prof. Gabriele Tolomei.
- **Core Reference:** _Resilient Distributed Datasets: A Fault-Tolerant Abstraction for In-Memory Cluster Computing_ (Zaharia et al., NSDI 2012).
- **Central Philosophy:** MapReduce solved cluster survivability by relying on disk replication; Apache Spark asks how to remain fast by keeping data in memory and tracking how to recompute it rather than replicating intermediate state.

```
  MapReduce Paradigm (Disk-Centric):
  Input ──► Map ──► Disk Shuffle ──► Reduce ──► HDFS Write ──► Read Disk ──► Map ──► ...

  Spark Paradigm (Memory-Centric Dataflow):
  Input ──► [RAM Pipeline: Map ──► Filter ──► Map] ──► [Shuffle Boundary] ──► [RAM Pipeline: Reduce] ──► Output
```

### 1.1 The MapReduce Bottlenecks

Lecture 1.2 identified three structural bottlenecks in MapReduce:

1. **Disk-Heavy Execution:** Intermediate data between Map and Reduce phases is written to local disk and re-read, creating heavy disk I/O overhead.
2. **Rigid Two-Stage Pipeline:** Workloads are constrained to a fixed $\text{Map} \rightarrow \text{Shuffle} \rightarrow \text{Reduce}$ shape.
3. **High Latency across Multi-Job Chains:** Complex workflows require chaining independent MapReduce jobs, forcing a full write and read cycle to HDFS/GFS (with 3× replication) between every job boundary.

### 1.2 Target Workloads for Spark

Spark was designed to optimize two workload patterns that perform poorly under MapReduce:

- **Iterative Algorithms:** Machine learning loops (e.g., stochastic gradient descent) and iterative graph processing (e.g., PageRank) that scan the exact same dataset repeatedly across dozens of iterations.
- **Interactive & Exploratory Analytics:** Ad-hoc queries where analysts need rapid response times across cached datasets loaded once into cluster RAM.

## 2. Resilient Distributed Datasets (RDDs) (§2)

### 2.1 Definition & Properties

The **Resilient Distributed Dataset (RDD)** is Spark's fundamental data abstraction:

- **Immutable:** An RDD cannot be mutated in place after creation. Any modification yields a brand-new RDD.
- **Partitioned:** Elements are split into discrete partitions distributed across nodes, forming the primary unit of parallel processing.
- **Resilient via Lineage:** Fault tolerance is achieved by recording the sequence of derivations (lineage graph) used to build the RDD, enabling lost partitions to be recomputed on demand without data replication.

```
Aspect               GFS/HDFS Storage Blocks (Lec 1.1)    Spark RDD Partitions (Lec 1.3)
------------------------------------------------------------------------------------------
Primary Purpose      Durable physical disk storage        Logical distributed compute abstraction
Fault Tolerance      3× physical data replication Lineage-based recomputation graph
Modification Model   Append-only files               Strictly immutable collections
Creation             Direct byte writes to disk           `textFile()` from storage or `parallelize()`
```

### 2.2 Memory Caching & Persistence Levels

To support rapid reuse across iterative loops or interactive queries, RDDs can be explicitly cached in memory using `.cache()` or `.persist()`.

|Persistence Level|Behavior & Trade-offs|
|:--|:--|
|**`MEMORY_ONLY`**|Stores partitions as deserialized Java objects in RAM. Fastest performance; if partitions do not fit, excess is recomputed on demand via lineage.|
|**`MEMORY_AND_DISK`**|Stores partitions in RAM; spills excess partitions to local disk to prevent recomputation overhead.|
|**`DISK_ONLY`**|Persists partitions strictly to local disk, bypassing memory pressure at the expense of disk I/O latency.|

## 3. Programming Interface: Transformations vs. Actions (§3)

Spark explicitly separates operations on RDDs into two distinct categories:

```
  Transformations (Lazy)                     Actions (Eager)
  ┌─────────────────────────────────┐        ┌─────────────────────────────────┐
  │ map(), filter(), flatMap()      │        │ collect(), count(), take()      │
  │ groupByKey(), reduceByKey()     │ ─────► │ reduce(), saveAsTextFile()      │
  │ union(), join()                 │        │                                 │
  │ (Returns new RDD / Builds DAG)  │        │ (Triggers Execution / Output)   │
  └─────────────────────────────────┘        └─────────────────────────────────┘
```

### 3.1 Transformations (Lazy)

Transformations derive a new RDD from existing RDDs. Calling a transformation does not compute data or execute tasks; it updates the internal logical lineage DAG.

- **Examples:** `map(f)`, `filter(f)`, `flatMap(f)`, `distinct()`, `union(other)`, `reduceByKey(f)`, `join(other)`.

### 3.2 Actions (Eager)

Actions trigger physical execution across the cluster, materializing data and returning non-RDD values to the driver program or persisting output to storage.

- **Examples:** `count()`, `collect()`, `take(n)`, `reduce(f)`, `saveAsTextFile(path)`.

### 3.3 Code Walkthrough: Word Count

```
# Transformations: Only builds the logical DAG (no disk/network I/O triggered yet)
lines = sc.textFile("hdfs://documents/")
words = lines.flatMap(lambda line: line.split())
pairs = words.map(lambda word: (word, 1))
counts = pairs.reduceByKey(lambda a, b: a + b)

# Action: Triggers DAG compilation, stage division, task scheduling, and execution
result = counts.collect()
```

_Until `.collect()` is called, `lines`, `words`, `pairs`, and `counts` are lightweight RDD descriptions tracking logical derivations._

## 4. Lazy Evaluation & The Execution DAG (§4)

### 4.1 Benefits of Lazy Evaluation

By deferring execution until an action is invoked, Spark inspects the entire query graph as a unified pipeline:

1. **Operator Fusion (Pipelining):** Consecutive element-wise operations (e.g., `map(f) -> filter(g) -> map(h)`) are fused together and evaluated in a single pass per partition, eliminating temporary intermediate buffers.
2. **Avoiding Unnecessary Work:** If an action requests partial data (e.g., `take(5)`), the engine optimizes physical scheduling to avoid evaluating unnecessary partitions.

### 4.2 Logical Plan to Physical Execution Pipeline

```
  RDD Transformations ──► Logical Lineage DAG ──► DAG Scheduler ──► Physical Stages ──► Parallel Tasks
```

1. **Logical Lineage DAG:** Tracks parent-child RDD pointers and transformation references.
2. **DAG Scheduler:** Analyzes dependencies across the graph, divides the DAG into physical stages at shuffle boundaries, and emits tasks per partition.
3. **Task Execution:** Tasks are assigned to worker executors using data locality preferences (preferring nodes holding cached RAM partitions or local HDFS blocks).

## 5. Narrow vs. Wide Dependencies (§5)

The physical structure of a Spark stage is determined by the classification of dependencies between parent and child RDD partitions.

```
  Narrow Dependency (Pipelinable):            Wide Dependency (Requires Shuffle):
  Parent RDD           Child RDD             Parent RDD           Child RDD
  ┌──────────┐        ┌──────────┐           ┌──────────┐        ┌──────────┐
  │Part 0    ├───────►│Part 0    │           │Part 0    ├──┬────►│Part 0    │
  ├──────────┤        ├──────────┤           ├──────────┤  │     ├──────────┤
  │Part 1    ├───────►│Part 1    │           │Part 1    ├──┼─┬──►│Part 1    │
  └──────────┘        └──────────┘           └──────────┘  └─┼───┴──────────┤
                                                           └───►│Part 2    │
                                                                └──────────┘
```

### 5.1 Narrow Dependencies

- **Definition:** Each partition of the child RDD depends on a small, fixed number (typically exactly one) of partitions of the parent RDD.
- **Operations:** `map()`, `filter()`, `flatMap()`, `union()`.
- **Execution Characteristic:** Computed locally on worker nodes without network data transfers. Multiple narrow transformations are pipelined together within the **same physical stage**.

### 5.2 Wide Dependencies

- **Definition:** A partition of the child RDD depends on data distributed across multiple (or all) partitions of the parent RDD.
- **Operations:** `groupByKey()`, `reduceByKey()`, `join()`, `distinct()`.
- **Execution Characteristic:** Requires an all-to-all **shuffle operation** across the cluster to partition and group records by key. Every wide dependency forces a **hard physical stage boundary**.

### 5.3 Optimization Rule: Pre-Aggregation

To minimize network overhead during shuffle operations, algorithms should favor `reduceByKey()` over `groupByKey()`. `reduceByKey()` performs local map-side pre-aggregation before transferring data across the network (acting like a MapReduce Combiner), whereas `groupByKey()` transfers unaggregated records across the cluster.

## 6. Lineage Tracking & Fault Tolerance (§6)

### 6.1 Fault Tolerance via Recomputation vs. Replication

When a worker node crashes and loses an RDD partition, Spark recovers state without maintaining physical data replicas.

```
Aspect               Storage Replication (GFS/HDFS)       Lineage Recomputation (Spark)
------------------------------------------------------------------------------------------
Primary Mechanism    3× physical block copies        Compact DAG derivation history
Storage Overhead     200% excess storage cost   Negligible metadata graph overhead
Recovery Execution   Read alternate block copy       Reapply operations to parent partition
Trade-off            Higher storage costs, fast recovery  Zero storage overhead, compute CPU cost on failure
```

### 6.2 Partition Recovery Algorithm

1. The DAG Scheduler catches a task failure resulting from a missing partition.
2. The scheduler inspects the lost partition's lineage graph to locate its parent partition.
3. If parent partitions are present in memory/disk, Spark re-evaluates only the missing child partition.
4. If parent partitions are also missing, recovery recurses backward along the lineage chain until reaching a valid cached partition or source storage block.

```
  Lineage Recovery Path:
  Source Storage Block ──► [Parent RDD Partition] ──► (Re-apply filter) ──► [Recovered Child Partition]
```

### 6.3 Truncating Lineage via Checkpointing

In long-running iterative programs (e.g., 100 iterations of PageRank), lineage graphs grow deep. Recomputing a lost partition near the end of a deep DAG can cause cascading recomputation back to the initial input.

- **Checkpointing Mechanism:** `.checkpoint()` evaluates the RDD and saves its contents to durable, replicated distributed storage (e.g., HDFS).
- **Lineage Reset:** Once written to HDFS, Spark truncates the RDD's lineage graph. Subsequent failure recoveries start from the checkpointed snapshot rather than the original source file.

### 7.3 Limitations of RDDs & Future Horizons

While RDDs resolve MapReduce's disk and pipeline rigidity bottlenecks, pure RDD APIs present limitations:

- **Low-Level Abstraction:** Functional transformations on raw Java/Python objects require manual optimization.
- **Lack of Schema Awareness:** The engine cannot inspect internal tuple structures to apply query optimization techniques (e.g., columnar layouts or predicate pushdown), motivating **DataFrames** and **Spark SQL**.
- **Unbounded Streaming:** Pure RDD batch semantics paved the way for dedicated continuous processing systems like **Apache Flink**.
